# Agent Swarm — Handoff, 2026-09-22

For the operator, Gemini and ChatGPT. Everything below was measured on 2026-09-22, not recalled.

---

## 1. The directive

**Get the pipeline working, end to end, and make the work visible in the hub chat.**

Priorities, in order:

1. **A working pipeline.** A task goes from a chat message to a merged commit without an operator doing anything the system should have done itself. Two stages have never been proven on the current deployment — integration and autonomous merge. Everything else has.
2. **Surface the work in the hub chat.** Progress, verdicts, refusals and blockers should appear in the room as they happen, with regular updates, so the operator and the other agents can see state without reading a database.
3. **Take direction in the hub chat.** From the operator, and — where the design allows it — from each other. See §6 for what currently does and does not work here; this is not fully possible today and needs a decision.
4. **Efficiency.** Fewer round trips, fewer wasted model calls, less operator translation.

**External security is an explicitly low priority.** This runs on a private LAN with one operator. Do not spend effort on threat models, credential rotation, network exposure, auth hardening or anything shaped like defending against an outside attacker. If a choice is between "more secure against strangers" and "the pipeline runs", pick the pipeline.

**One distinction that is not security and must not be dropped:** the ledger meaning what it says. Events like "this was reviewed", "this merged", "this candidate was approved" are the system's memory. When those become unreliable, nothing can be debugged, because every later question is answered from a record that might be wrong. Several open issues (#58, #64, #68) are about that, and they are *correctness* work, not hardening. Keep them. The test is simple: if a property stops an outsider, deprioritise it; if a property stops *us* from being misled by our own records, keep it.

**Production and development are separate checkouts as of 2026-09-22.** They used to be the same directory, which meant a supervisor restart could start production on whatever feature branch happened to be checked out. If you change branches, you are changing development only.

### Commands that matter

```bash
# from C:\swarm-prod\agent-swarm
./swarm_ctl.sh status | pause "reason" | resume | start | stop | ensure
./worker_ctl.sh preflight {claudecode|gemini|chatgpt}   # verifies deployed build == this checkout
./worker_ctl.sh admin <controller_admin args>           # repair, retry, cancel, show, events
DEPLOY_PYTHON=/c/Python311/python ./deploy_controller.sh  # runs the gate, then deploys
```

`preflight` is the parity check: it compares the controller's *running* build, its *on-disk* build, and what this checkout would deploy. All three must agree. A deploy that copies files without restarting fails it, which is the point.

## 4. How to create a task — the exact format

Acceptance run 1 took **four rejected attempts** to discover this. Every refusal was correct, cheap and clear; none was discoverable in advance (that is #67). Use this template:

```
@swarm <title, under 200 characters>
project: agenthub
base: <full 40-character sha — the controller has no checkout and cannot resolve a branch name>
paths: <writable paths>
context: <read-only paths, optional>
proof: <optional; defaults to branch_only>

<objective, after a blank line>
```

The controller replies with a draft and a confirm line. Nothing runs until:

```
@swarm confirm CMD-<id>
```

Other commands: `@swarm retry T-<id>`, `@swarm cancel T-<id> <reason>` → `@swarm confirm-cancel T-<id> <code> <reason>`, `@Gemini status T-<id>`.

**Only `admin` and `operator` senders are parsed as commands.** A worker's message is never a command.

## 6. Surfacing work in the chat, and taking direction there

### What already works

The **narrator** runs inside the supervisor and posts the lifecycle to the room as it happens. During acceptance run 1 it posted ten messages covering every transition, including the blocked excursion and the repair. That is the "regular updates" requirement, already met for task lifecycle.

### What does not work yet

**Agents cannot take directives from each other in the chat.** `hub.py` parses chat commands only from `admin` and `operator` senders; a worker's message is stored and never parsed. `@Gemini` explicitly cannot start work — it reviews through the pipeline only.

This was deliberate: agents replying to one another caused autonomous loops and unnecessary paid API calls, so it was removed. **The directive asks for agent-to-agent direction in chat, and that is a design change with a known failure history.** It needs a decision before anyone implements it. A safe shape, if wanted: agents may *post* freely (they already can), but only the operator's messages create or advance work — with the possible exception of a narrow, rate-limited, explicitly-named command set.

### What is missing for visibility

- Progress *within* a long stage. The narrator reports transitions, not "still authoring, 3 minutes in".
- A periodic heartbeat to the room — "nothing in flight" is useful information when the swarm has been idle for six days and nobody noticed.
- Failures that happen outside a task's lifecycle (a worker crash-looping, a preflight failing) do not reach the room at all.

## 7. Working agreements

These came out of the last two days and are worth keeping.

**Verify the artifact, not the report.** Claims get checked against the running system before they are acted on. Three times in two days, a plausible remedy turned out to be wrong: restoring a cleared approval column would have laundered a rejected candidate; a packet-hash gate for relayed verdicts could not be built inside the ledger-only boundary; and a "never fetches" claim was enforced only against explicit subcommands while git's own promisor fetch went unguarded. All three were caught by review, not by the author.

**An action isn't done until something outside the claim says so.** Both Gemini and Claude asserted completed actions that had not happened — a `curl` that was never run, and a post that was never sent. Check for a receipt: an HTTP status, a merge SHA, a CI conclusion, a process ID.

**Reviews name an exact SHA.** A verdict applies to one candidate. If a new commit is pushed, the old verdict is void and the packet must be rebuilt.

**Mutation-test the guards.** A test that passes when the guard is removed is not covering it. Every guard added in the last two days was verified this way, and it caught two tests that passed for the wrong reason.

**Two different things are called "Gemini".** `gemini_worker.py` on OfficePC holds the API key and a Hub credential, claims controller-issued activations, and lands in the ledger. The operator's manual Gemini chat has no shell, no LAN route and no credential — anything it writes that looks like a command is generated text. It will say it ran something and nothing will have happened. Same for ChatGPT.

**Relayed verdicts leave no ledger evidence.** Three consecutive merges (`a3e9537`, `206fce8`, `74dfaef`) were approved by manually relayed verdicts. None has a review activation or recorded verdict. That is #58, and until it is fixed, say so wherever a merge's provenance is recorded.

## 8. Known traps

- **The scheduled task fires every 5 minutes** and re-execs `swarm_ctl.sh start` from the production path. Stop production without disabling it and it comes back within five minutes.
- **`REVIEW_REPO_OVERRIDE` does nothing on the runtime path.** `worker_ctl.sh` reads it for a hand-started worker; the supervisor path uses `REVIEW_REPO`. The code says so at `swarm_ctl.sh:128`.
- **Worker `.state` files are hub message cursors.** They currently read ~1324. A fresh checkout starting at 0 replays the entire chat history.
- **`DEFAULT_FILE_VIEW` is 50,000 characters** and a module past it cannot be given to a worker as a task. `activations.py` hit it and had to be split (#61). `chatgpt_worker.py` is at 99.7%. `tests/test_supervisor.py` is *already over* and the guard cannot see it, because it only checks root modules.
- **`plan.py` is over the limit too** and is a recorded exclusion.
- **The controller has no checkout.** It cannot resolve a branch name, read a file, or run git. Every design that needs those must put the work in a worker and the evidence in the ledger.

## 9. Permissions in force

Unchanged, and to be kept:

- Full read/write across the swarm checkouts, Tower, PiNAS and all OfficePC drives.
- Shell, tests, git, and `gh` operations.
- SSH to `tower.local`.
- Deploys and restarts through the supported control scripts.
- **The merge and deploy gate remains the operator's.** Merging a PR, deploying to Tower and issuing a real task happen on the operator's explicit go-ahead. That gate is not a security control — it is how the operator stays informed, and it has caught real defects twice in two days.
