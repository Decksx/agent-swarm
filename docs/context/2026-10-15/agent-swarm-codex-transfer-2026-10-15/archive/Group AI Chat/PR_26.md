+"""Reporting a merge the controller never performed (#26).
+
+INTEGRATION_UNCERTAIN was reachable one way: an integration lease that lapsed
+mid-merge, leaving the controller unable to say from its own records whether
+the merge landed. T-INGRESS-05 reached the same question down a different
+road. The integrator refused the candidate for want of test evidence, the
+author budget ran out, the task escalated -- and minutes earlier an operator
+had merged the pull request by hand. The merge was on the target and no event
+in the ledger could say so, so the task was closed SUPERSEDED, which is the
+least wrong close available and still loses that the work succeeded.
+
+This module is the entrance to reconciliation for that case, and it is
+deliberately not a second way to complete a task. It moves a task to
+INTEGRATION_UNCERTAIN and stops; the reconcile route decides what actually
+landed, so "this merge is on the target" is established in one place no matter
+how the task arrived at the question.
+
+What can and cannot be checked
+------------------------------
+
+Nothing here has a working copy, so the merge itself is **not verified** and
+saying otherwise would be the whole problem with this feature. What the
+controller can check is its own ledger, and it checks three things there: that
+the task is somewhere a report makes sense, that the task carries an approval
+at all, and that the candidate a reporter names is the one that approval was
+issued against.
+
+The second is the load-bearing one. Without it, reporting a merge is a way to
+walk work nobody reviewed into the state that exists to trust reports, and
+from there into COMPLETE.
+
+`tasks.approved_candidate_sha` cannot answer the second or third question.
+`integration_rejected` is in `engine.APPROVAL_CLEARING`, so the column is NULL
+on precisely the tasks this module serves. The approval is read from the event
+log, where it happened, and the candidate from the review activation the
+controller issued -- never from the reporter. See `engine._approved_candidate`
+for why that distinction is the security property and not a preference.
+"""

+                "merged_by": merged_by,
+                "pull_request": pull_request,
+                "merged_at": merged_at,
+                "reason": reason,
+                "reported_by": actor,
+                "approval_seq": approval["seq"],
+                # No working copy, no verification. Said here so a reader of
+                # the log never has to infer it from the event's name.
+                "verified": False,
+            },
+        )
+
+    return {
+        "task_id": task_id,
+        "event_id": moved["event_id"],
+        "from_state": moved["from_state"],
+        "to_state": moved["to_state"],
+        "candidate_sha": approved,

+            f"confirmed on {target_ref}"
+        ),
+    }

## What was missing

Not an evidence protocol — one already exists. `POST /controller/tasks/{id}/reconcile`
takes `integration_reconciled_landed` / `_absent` / `reconciliation_failed`, and
`states.py` already records why a reconciled landing reaches COMPLETE through its own
event rather than `integration_completed`: "the ledger distinguishes an integration
observed by the integrator from one reconstructed afterwards. They are not the same
evidence."

What was missing is **reachability**. `INTEGRATION_UNCERTAIN` was entered only from
`INTEGRATING` via `integration_outcome_unknown` (lease expiry). T-INGRESS-05 reached the
same uncertainty down the other road — `integration_rejected` → `CHANGES_REQUESTED` →
`budget_exhausted` → `NEEDS_HUMAN` — and `NEEDS_HUMAN` had no edge into reconciliation.
The task was closed `SUPERSEDED`, which loses that the work succeeded.

## What this adds

One event and two transitions:

```
("NEEDS_HUMAN",       "out_of_band_merge_reported") -> INTEGRATION_UNCERTAIN, ADMIN
("CHANGES_REQUESTED", "out_of_band_merge_reported") -> INTEGRATION_UNCERTAIN, ADMIN
```

ADMIN rather than OPERATOR: a worker able to report its own out-of-band merge could walk
unreviewed work into a state that exists to trust reports.

`POST /controller/tasks/{id}/out-of-band-merge` (admin-gated) records the report, and the
existing reconcile route still decides what landed. Landing stays one decision in one
place, however the task arrived at the question.

## What it checks, and what it cannot

Three checks, all answerable from the ledger alone:

- the task is in `NEEDS_HUMAN` or `CHANGES_REQUESTED`;
- the task carries an approval in its log — without this, a report is a way to launder
  unreviewed work into COMPLETE;
- the candidate reported, if one is named, is the commit the controller issued the
  approved review against.

`tasks.approved_candidate_sha` cannot answer the last two: `integration_rejected` is in
`engine.APPROVAL_CLEARING`, so the column is NULL on precisely the tasks this serves. The
approval is read from the event log and the candidate from the review activation, never
from the reporter — the property `engine._approved_candidate` is written around.

**The merge itself is not verified and cannot be.** Nothing in the controller has a
working copy. The event kind says `reported`, the payload carries `verified: false` and
the authenticated `reported_by`, and the task stops in `INTEGRATION_UNCERTAIN` rather than
advancing.

## The payload

```json
{
  "merge_sha": "ea27537…", "candidate_sha": "607c5a2…",
  "target_ref": "refs/heads/main", "merged_by": "…", "pull_request": 11,
  "merged_at": "2026-09-12T22:57:58Z", "reason": "…",
  "reported_by": "admin", "approval_seq": 210, "verified": false
}
```

Answers the issue's "how did this land?", and by `approval_seq` + `source_event_id`, what
it was allowed to land against.

  `api.py` crossed `DEFAULT_FILE_VIEW` (52,300 > 50,000) and
  `test_a_module_a_task_writes_fits_in_one_file_view` says a module past the window is one
  the swarm cannot be given a task about. Split rather than raise the cap: the cap is paid
  by every prompt. api.py is 46,114 after.

  kind with none of the checks above. That widens

  widening be a decision rather than a drift — renamed and documented accordingly.

  unreviewed task reaching `INTEGRATION_UNCERTAIN` on a 200 — not with a crash.

## Open question

Reporting from `NEEDS_HUMAN` leaves the escalation unanswered: no `operator_response`
event and no version bump, so attempts authorized before the escalation stay valid. A
required `reason` is recorded in the payload instead. Pairing it with the version advance
`/operator-response` makes would mean that route's `NEEDS_HUMAN`-only precondition, and
`CHANGES_REQUESTED` would still need this route — so the dedicated route handles both.
Worth arguing before it ships.
